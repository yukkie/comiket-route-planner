# コミケ巡回プランナー

前回のNotion巡回リスト、Xのフォローリスト、参加告知、お品書き、公式配置図をまとめ、次回コミケ用のNotion巡回リストを作るプロジェクトです。

最終的に、コミケ当日にNotionを開くだけで次を判断できる状態を目指します。

- 次にどのサークルへ行くか
- 作家名とサークル名は何か
- 新刊単品と新刊セットのどちらを買うか
- いくら持っていけばよいか
- 訪問済み、購入済み、売切れ、見送りのどれか

## 現在地

このプロジェクトは開発途中です。現在のCLIは、複数のフォローリストJSONを統合し、前回Notionから取得したJSONの優先度・一言ジャンルをXハンドルで引き継いで、次回候補JSONを作るところまで動きます。X API・お品書き抽出・Notionへの再同期はまだ完成していません。

### 現在動くもの

- uvによる環境構築とCLI実行
- 前回CSVまたは正規化済みJSONの取り込み
- 作家・サークル候補の照合と同一イベント再同期
- ユーザーが編集した優先度、ジャンル、メモ、訪問状態、購入選択の保護
- `buy / candidate / skip`による確定額と候補込み最大額の計算
- 価格不明、配置不明、重複、セットと単品の二重計上候補の検出
- JSON、CSV、確認用HTMLの出力

### まだ動かないもの

- Notionから前回リストを取り込むCLIアダプタ
- 新しいNotion巡回リストの作成・再同期
- 配置済みのXフォローリストを読み込むアダプタ（実装済み）
- X公式APIからフォロー・投稿を取得するアダプタ
- 参加告知とお品書き投稿の自動探索
- お品書き画像から作家名、サークル名、商品、価格を抽出する処理
- 公式PDFからの配置・壁・シャッター候補判定

確認用HTMLはNotion同期が完成するまでの補助出力です。最終的な当日用画面ではありません。

## 完成時の利用フロー

```text
ユーザー
  ├─ 前回のNotionデータベースURLを指定
  ├─ Xフォローリストを data/raw/x/ に配置
  ├─ 対象イベント・日程を指定
  └─ 公式配置図PDFを配置
           │
           ▼
AI（Codex）
  ├─ 指定されたNotionだけを読み取る
  ├─ X上の参加告知・お品書き候補を判断する
  ├─ お品書き画像を読み、作家名・サークル名・商品・価格を候補化する
  └─ 曖昧な照合や読めない価格を要確認にする
           │
           ▼
Python CLI
  ├─ 入力を正規化する
  ├─ 前回のユーザー判断を保護して統合する
  ├─ 金額を計算する
  ├─ 重複・欠損・二重計上を検証する
  └─ Notion同期用データを確定する
           │
           ▼
ユーザー確認
  ├─ 曖昧な作家／サークル照合を確定
  ├─ 新刊単品／新刊セット／見送りを選択
  └─ 必要なら優先度・ジャンル・メモを修正
           │
           ▼
Notion巡回リスト
  ├─ 確定購入額
  ├─ 候補込み最大額
  ├─ 価格不明一覧
  └─ 当日の訪問状態
```

## ユーザーが行うこと

ユーザーにお願いする操作は、できるだけ次に限定します。

1. 対象イベントと参加日を伝える。
2. 前回リストの正確なNotion URLを伝える。
3. 取得済みXフォローリストを`data/raw/x/`へ置く。
4. 公式配置図PDFなど、必要な原本を`data/raw/`へ置く。
5. AIが出した要確認項目を確認する。
6. 新刊単品、新刊セット、候補、見送りを選ぶ。
7. 当日はNotionで訪問状態を更新する。

Codexは、ユーザーが指定していないNotionページやデータベースを勝手に検索して採用しません。URLが不明な場合は先にユーザーへ確認します。

## AIとスクリプトの役割分担

判断が必要な処理はAI、毎回同じ結果になるべき処理はPython CLIが担当します。

| 処理 | 担当 | 理由 |
|---|---|---|
| 前回Notion URLの指定 | ユーザー | 対象を勝手に決めないため |
| Xフォローリストの取得 | 当面はユーザー提供、将来はX API | 取得方式を交換可能にするため |
| 今回参加する可能性があるアカウントの選別 | AI | 告知文やプロフィールの文脈判断が必要 |
| 参加日・配置の候補抽出 | AI | 表記揺れや画像内文字があるため |
| 作家名とサークル名の分離 | AI＋ユーザー確認 | 同名・別名・合同サークルがあるため |
| お品書き画像の読解 | AI | 画像レイアウトと文脈判断が必要 |
| 新刊単品・新刊セットの識別 | AI＋ユーザー確認 | セット構成や特典表記が一定でないため |
| JSONスキーマ検証 | Python CLI | 決定的に判定できるため |
| ID生成・重複排除 | Python CLI | 再実行時も同じ結果にするため |
| 前回データとの統合 | Python CLI | 手動編集の保護ルールを確実に守るため |
| 確定額・最大額の計算 | Python CLI | 計算ミスを防ぐため |
| セットと単品の二重計上検査 | Python CLI | 商品構成が確定した後は機械的に検査できるため |
| 低信頼結果の最終判断 | ユーザー | AIの推測を確定情報にしないため |
| Notionへの追加・更新 | Python CLI＋Notion接続 | 冪等なupsertと差分表示が必要なため |

AIは不明な値を埋めません。作家名しか分からない場合、サークル名は作家名で代用せず`unknown`として確認対象にします。価格不明も0円として扱いません。

## 入力データ

### 前回のNotion巡回リスト

前回のNotionは、ユーザー自身が判断した次の情報を引き継ぐために使います。

- 作家名
- Xアカウント
- 優先度
- 一言ジャンル
- メモ
- 前回の配置
- 前回の購入実績

前回の`購入済`は履歴として保存しますが、次回イベントの訪問状態には引き継ぎません。次回イベントはすべて`未訪問`から始めます。

### Xフォローリスト

当面は「イベント参加者をゆるく抽出する」既存処理で取得したJSONを入力にします。

将来はX公式APIアダプタへ置き換えます。後工程が取得方式に依存しないよう、どちらも共通のアカウント・投稿形式へ正規化します。

```text
現在:   手動配置したフォローリストJSON ─┐
将来:   X公式APIレスポンス ────────────┼─> 共通Xデータ ─> 後続処理
予備:   ユーザー提供エクスポート ───────┘
```

フォローリストだけでは今回の参加、配置、サークル名、頒布物、価格は確定しません。各アカウントの参加告知とお品書き情報を追加で確認します。

### お品書き

お品書きの投稿本文と画像から、最低限次を抽出します。

- 作家名
- サークル名
- 参加日
- 配置
- 新刊単品の商品名と価格
- 新刊セットの商品名と価格
- セットに新刊単品が含まれるか
- 全年齢／成人向けの最小限の区分
- 根拠となる投稿URL
- 抽出の信頼度と要確認理由

商品や価格を読み取れない場合は、推測で確定せず要確認へ送ります。

### 公式配置図PDF

スペースコードからホール、壁、島中、シャッター候補を判定するために使います。巨大列の実際の最後尾や待ち時間は公式配置図からは分からないため、MVPでは扱いません。

## データの保存場所

```text
data/
├── raw/                 # 入力原本。上書きしない
│   ├── x/               # フォローリスト、投稿、X APIレスポンス
│   ├── notion/          # 指定Notion DBの取得結果
│   ├── menus/           # お品書き画像
│   └── maps/            # 公式配置図PDF
├── derived/             # AI抽出候補、要確認レポート、配置索引
└── events/              # イベント単位の統合済みEventPlan JSON
```

`data/raw/`は取得した値を極力そのまま残します。意味の変換や英語列挙値への変換は`data/derived/`以降で行います。

個人用のフォローリスト、Notion取得結果、投稿データ、画像、認証情報はGitへコミットしません。

## JSON・Markdown・Notionの役割

| 形式 | 役割 |
|---|---|
| JSON | 型、ID、根拠、商品、価格を保持して再実行・再同期するための統合データ |
| Markdown | 不明値、競合、低信頼抽出などを人間が確認するレポート |
| Notion | ユーザーが購入方針や進捗を編集し、当日に使う画面 |
| HTML | Notion同期が利用できない場合の確認・オフライン補助出力 |

ローカルJSONだけを唯一の正本にはしません。役割ごとに正本を分けます。

- Xやお品書きから得た事実と根拠: ローカルの原本・統合JSON
- 優先度、ジャンル、購入方針、メモ、訪問状態: Notion上のユーザー編集
- 金額、警告、表示用小計: 入力から再計算できる生成値

## 最初に作るNotion巡回リスト

最初のMVPでは、当日の操作を単純にするため一つの巡回リストへまとめます。内部JSONでは複数商品を保持し、Notionには主要な購入候補を要約して出します。

| Notion列 | 内容 | 編集者 |
|---|---|---|
| 作家名 | Xアカウントの人物・作家名 | AI候補→ユーザー確認 |
| サークル名 | お品書き・告知に明記されたサークル名 | AI候補→ユーザー確認 |
| Xアカウント | 安定したハンドルまたはユーザーID | スクリプト |
| 日付 | 1日目／2日目 | AI候補→ユーザー確認 |
| ホール | 東・西・南のホール | スクリプト |
| 配置 | スペースコード | AI候補→ユーザー確認 |
| 配置種別 | シャッター候補／壁／島中／不明 | AI＋スクリプト |
| 優先度 | A／B／C／未設定 | ユーザー |
| 一言ジャンル | 当日判断用の短い分類 | ユーザー優先、AI補助 |
| 新刊単品 | 商品名 | AI候補→ユーザー確認 |
| 新刊単品価格 | 円単位。価格不明は空欄 | AI候補→ユーザー確認 |
| 新刊セット | セット名 | AI候補→ユーザー確認 |
| 新刊セット価格 | 円単位。価格不明は空欄 | AI候補→ユーザー確認 |
| 購入方針 | 単品／セット／候補／見送り／未設定 | ユーザー |
| 確定小計 | 確定した購入方針から計算 | スクリプト |
| 最大小計 | 候補を含めて計算 | スクリプト |
| 価格不明 | 選択中の商品に価格不明があるか | スクリプト |
| 訪問状態 | 未訪問／購入済／売切れ／見送り | ユーザー |
| メモ | 優先理由や当日注意点 | ユーザー |
| 根拠URL | 参加告知・お品書き投稿 | スクリプト |
| 要確認 | サークル名、配置、価格などの未確定理由 | AI＋スクリプト |

頒布物が増えて一行で扱えなくなった段階で、巡回先DBと頒布物DBの二つへ分割しRelationで結びます。最初から複雑な二DB構成にはしません。

## 予算の計算

内部JSONでは各商品に次の状態を持たせます。

- `buy`: 買うと決めた
- `candidate`: 当日候補
- `skip`: 買わない

```text
確定購入額       = buyのうち価格が分かる商品の合計
候補込み最大額   = buyとcandidateのうち価格が分かる商品の合計
価格不明件数     = buyまたはcandidateで価格が不明な商品の件数
```

価格不明は0円として計算しません。新刊セットと、そのセットに含まれる新刊単品が両方選ばれている場合も自動で片方を消さず、二重計上候補としてユーザーへ確認します。

## 再同期で守るもの

同じイベントへX投稿やお品書きを追加取得しても、次のユーザー編集は上書きしません。

- 優先度
- 一言ジャンル
- 購入方針
- メモ
- 訪問状態
- ユーザーが確認済みにした作家名・サークル名

値の優先順位は次のとおりです。

1. 今回イベントでのユーザー編集
2. ユーザー確認済みの抽出値
3. 前回Notionの手動値
4. 公式情報・明示的な参加告知
5. お品書き画像からの抽出
6. プロフィールや一般投稿からの推定

## 現在のCLI

Python 3.10以上とuvを使用します。

```powershell
uv sync
uv run comiket-plan --help
```

現在実装済みのコマンドは次のとおりです。

```text
comiket-plan init
comiket-plan import-previous
comiket-plan build-next
comiket-plan reconcile
comiket-plan validate
comiket-plan export
```

例:

```powershell
uv run comiket-plan init EVENT-day1 `
  --name "Comic Market" `
  --day 1 `
  --output data/events/EVENT-day1.json

uv run comiket-plan import-previous `
  data/events/EVENT-day1.json `
  previous.csv

uv run comiket-plan validate `
  data/events/EVENT-day1.json `
  --report data/derived/EVENT-day1-review.json
```

提供済みフォローJSONと前回Notion取得JSONから仮想C109候補を作る例です。`--follow`は複数回指定でき、同じXハンドルは1件に統合されます。`--profile-pattern C108`は表示名・自己紹介にC108があるプロフィールだけを抽出し、`--include-previous-only`は前回リストにしかいない候補も追加します。

```powershell
uv run comiket-plan build-next C109 `
  --follow data/フォローリスト_20260815_0847.json `
  --follow data/フォローリスト_20260815_0851.json `
  --previous data/raw/notion/c108.json `
  --profile-pattern C108 `
  --include-previous-only `
  --output data/derived/c109-virtual.json `
  --report data/derived/c109-virtual-report.json
```

フォローJSONの`name`は作家名候補です。サークル名は確定扱いにせず、内部JSONでは`circle_name_confirmed: false`、Notionでは空欄＋`サークル名要確認`として扱います。

Notionへの再同期、X API、お品書き、配置図のコマンドは今後追加します。READMEに書かれていても、上の実装済み一覧にないコマンドはまだ利用できません。

## 目標とする実行方法

最終的には、ユーザーがCodexへ次のように依頼するだけで一連処理を開始できる状態を目指します。

```text
$comiket-route-planner を使って次回コミケの巡回リストを作って。
前回NotionはこのURL。
フォローリストと公式PDFは data/raw/ に置いた。
```

Codexは入力を確認し、不足しているURLやイベント日程があれば勝手に探さずユーザーへ質問します。その後、AI処理とCLI処理を使い分け、要確認レポートを提示してからNotionへ反映します。

## 次の実装順序

1. 実データをGit対象外の`data/raw/`へ整理する。
2. 指定された前回Notionデータベースだけを読み取るアダプタを作る。
3. 前回Notion列を作家名として正しく取り込み、サークル名と分離する。
4. 提供済みXフォローリストの形式を正規化するアダプタを作る。
5. X取得元を差し替えられるインターフェースを作る。
6. 参加告知・お品書き候補を収集する。
7. お品書きから新刊単品・新刊セット・価格を抽出する。
8. 要確認レポートをユーザーが確認する。
9. Notion巡回リストを新規作成し、再同期できるようにする。
10. 公式配置図の索引化を追加する。

最初の完了条件は「前回Notion＋提供済みフォローリスト＋お品書き情報から、作家名・サークル名・単品／セット価格・予算を持つ次回Notion巡回リストを作れること」です。
