# コミケ巡回プランナー：プロジェクト概要

## 1. 目的

前回の巡回リスト、X（旧Twitter）のフォロー・投稿情報、公式会場PDF、お品書き画像をまとめ、コミケ当日に使える購入・巡回リストを作る。

完成したリストは、少なくとも次の問いに答えられるものとする。

- どのサークルへ行くか
- どの順番・優先度で回るか
- 何を買う予定か
- 最低いくら、候補込みで最大いくら必要か
- 訪問後に購入済み・売切れ・見送りのどれになったか

## 2. 背景と課題

Xのフォロー一覧だけでは、コミケ参加の有無、配置、サークル名、頒布物、価格、ユーザー固有の優先度を確定できない。前回リストにはユーザーの判断があるが、今回の参加状況やお品書きは古い。公式PDFは配置判定に強い一方、商品情報を持たない。

したがって、複数の情報源を役割分担させ、AIの推定とユーザーの意思決定を混ぜずに統合する必要がある。

## 3. 想定ユーザー

- 自分がフォローしている作家・サークルを中心に巡回したい参加者
- 前回の優先度やジャンル分類を次回へ引き継ぎたい参加者
- お品書きから購入候補と必要現金を事前に把握したい参加者
- 当日はスマートフォンで素早く状態更新したい参加者

## 4. 入力

| 入力 | 主な役割 |
|---|---|
| 前回リスト | 優先度、一言ジャンル、別名、過去の判断を引き継ぐ |
| Xのフォロー一覧 | 今回の候補となる作家・サークルを列挙する |
| Xのプロフィール・投稿 | 参加日、配置、お品書き投稿、サークル名の候補を得る |
| お品書き画像 | サークル名、頒布物、価格、セット構成、成人向け／全年齢を抽出する |
| 公式会場PDF | スペースコードをホール・壁・シャッター前・島中などへ解決する |
| ユーザー編集 | 優先度、ジャンル、購入選択、メモ、訪問状態を確定する |

入力はAPIに限定しない。CSV、JSON、PDF、画像、既存のNotion/表計算エクスポートなど、ユーザーが正当に取得したファイルを利用できる構成にする。

## 5. 出力

- イベント単位の正規化データ（JSONを基準とする）
- 当日用ビュー（Notion、CSV、HTMLなど。実装時に選択）
- 要確認一覧（重複、低信頼マッチ、価格不明、配置不明）
- 確定購入額、候補込み最大額、価格不明アイテム数
- 次回へ引き継げる結果ログ

当日用ビューの推奨列は次のとおり。

`優先度 / 訪問状態 / 配置 / 壁区分 / サークル名 / 作家名 / 一言ジャンル / 購入予定 / 小計 / 最大 / メモ / 根拠リンク`

## 6. 重要なプロダクト原則

### ユーザー判断を最優先する

フォロワー数や推定人気度だけで優先度を変更しない。ユーザー編集、前回リスト、AI推定の順で優先する。

### 同一イベントの再同期で進捗を壊さない

新しいイベントの作成時だけ進捗を初期化する。同じイベントの再同期では、購入済みなどの手動状態を維持する。

### 不明を不明のまま扱う

価格不明を0円として合計しない。サークル名や配置を推測で確定しない。推定値には根拠と信頼度を持たせる。

### 商品選択を可変にする

各アイテムは `buy`（買う）、`candidate`（候補）、`skip`（買わない）を持つ。当日に選択を変えられるようにする。

### 成人向け情報を最小化する

公開情報をジャンル・年齢区分の判定に利用する場合でも、必要以上に露骨な本文や画像を保存・再生成しない。中立的な短い分類へ圧縮する。

## 7. MVPの範囲

- 前回リストの取り込み
- ユーザー提供のXエクスポートまたは取得可能な投稿データの取り込み
- 公式PDFからの配置インデックス生成
- お品書き画像からの候補抽出と人手確認
- レコード統合と手動編集保護
- アイテム別の購入状態と金額集計
- 当日用ビューの出力

## 8. MVPでは扱わないこと

- 搬入数が明示されていない場合の在庫数断定
- 売切れ時刻の保証
- リアルタイムの列位置・待ち時間の自動追跡
- Xのアクセス制限や認証を回避する取得
- AIだけでの完全自動購入判断
- 厳密な最短巡回路の保証

売切れリスクやルート最適化は、十分な履歴・現地データが集まってから段階的に追加する。

## 9. 想定利用フロー

1. イベント名と参加日を作成する。
2. 前回リストを取り込み、優先度・ジャンル・別名を継承する。
3. X情報から今回の参加候補と告知投稿を集める。
4. 公式PDFを解析し、配置インデックスを作る。
5. お品書きからサークル名、商品、価格を抽出する。
6. 曖昧な照合と抽出結果をユーザーが確認する。
7. 商品を「買う／候補／買わない」に設定する。
8. 確定額と最大額を確認し、当日用ビューを出力する。
9. 当日は訪問状態と商品選択を更新する。
10. 結果を次回用の履歴として保存する。

## 10. 成功条件

- 当日に「次にどこへ行き、何を買うか」をスマートフォン上で即座に判断できる。
- 確定購入額と候補込み最大額がアイテム明細と一致する。
- 再同期後もユーザーが付けた購入済み・優先度・購入選択が消えない。
- AI推定の出典を追跡でき、誤りを人手で訂正できる。
- 次回イベントで前回の判断と結果を再利用できる。

## 11. 引継ぎ時の未決事項

- 当日用ビューの第一ターゲットをNotion、静的HTML、スプレッドシートのどれにするか
- Xデータの取得方式（公式API、ユーザーエクスポート、手動投入）の優先順位
- 公式PDFの具体的な版面に対する壁・シャッター前判定ルール
- 同一商品をセットと単品の両方で選んだ場合のUIと警告方法
- 現金以外の決済手段を合計表示へ含めるか
- 複数日・複数同行者への対応時期

未決事項は実装者が固定仕様として決め打ちせず、MVP着手前にユーザーへ確認する。
